# 最も効率的なモデル配置戦略(一例)

> **注**: これは作者の環境(Claude サブスク + Codex サブスク + Kimi/GLM coding plan
> という特定の契約状況)を前提に、GPT-5.6 Sol の Deep-Research で導いた配置の一例。
> 契約・料金・用途が違えば最適解も変わる。integ.conf の書き方の参考として同梱している。

## エグゼクティブサマリー

最適構成は、**Fable-5をコントロールプレーン、他モデルをデータプレーン**として扱う形である。

- **Fable-5**：方針決定、タスク分解、採否判断、最終レビュー
- **gpt-5.6-sol**：難しい推論、デバッグ、独立検証、CTF/security
- **Opus-5[1m]**：巨大コンテキスト、ログ・コードベース横断、Claude限定ツールを伴う難作業
- **Kimi**：仕様が固まった後の実装、パッチ生成、反復修正
- **Terra／Sonnet**：通常難度の汎用ワーカー
- **Luna／GLM-4.5-air／Haiku**：検索補助、分類、要約、バルク処理

定額環境なので、単純な「最高性能モデルの温存」よりも、**失効までの時間、残量、タスク適性、ベンダー多様性**を同時に最適化すべきである。現在の使用率ならFableを過度に節約する必要はないが、機械作業に使うのは依然として非効率である。

## 1. ロール別モデル配置

| ロール | 第一選択 | 第二選択・補助 | 根拠 |
|---|---|---|---|
| トップ／判断／親 | **claude-fable-5** | gpt-5.6-sol | Fableは曖昧な要求の整理、委譲、成果物の採否判断に集中させる。独立した反証が必要な場合はSolを別ベンダーの第二判定者にする。 |
| 難しい設計・デバッグ | **gpt-5.6-sol** | Fable、Opus-5[1m] | 深い推論や仮説検証はSolに向く。巨大な証拠集合を直接読む必要があればOpusへ、最終的な方針決定はFableへ戻す。 |
| 実装ワーカー | **kimi-for-coding** | gpt-5.6-terra、Sonnet-5、Sol | 受け入れ条件が明確な実装、テスト追加、局所的リファクタはKimiを優先。設計判断を含む実装はTerra/Sonnet、難バグはSolへ昇格する。 |
| 長文コンテキスト | **claude-opus-5[1m]** | Solへ圧縮ハンドオフ | 全ログ、巨大diff、複数仕様書、モノレポ横断はOpusが主担当。ただし1M枠を「無差別投入」の理由にせず、索引化と段階要約を併用する。 |
| background／fast | **glm-4.5-air** または **gpt-5.6-luna** | Claudeツールが必要ならHaiku-4.5 | ファイル候補抽出、分類、フォーマット変換、短い要約などは軽量モデルへ。WebSearch/ToolSearchを使うバックグラウンド処理だけHaikuに固定する。 |
| 通常subagent | **gpt-5.6-sol** | Kimi、Terra、Opus | 親と異なるベンダーのSolを標準の批判的subagentにすると、同一モデル由来の見落としを減らせる。コードを書く場合はKimiへ明示的に切り替える。 |
| CTF／security | **Sol：推論・攻撃仮説**、**Opus：長大ログ解析** | Kimi：PoC・解析コード、Fable：最終レビュー | 推論、ログ処理、コード生成、採否判断を分離する。重要な脆弱性判断は、SolとFableまたはOpusのクロスベンダー二重確認を行う。 |
| 調査／文書 | **Sonnet-5** | Opus、GLM-5.2、Fable | Claude限定検索ツールを使う調査はSonnetが効率的。大量資料はOpus、初稿はGLM、重要文書の構成と最終校閲はFableが適する。 |
| 大量・低価値バルク | **GLM-4.5-air／Luna** | GLM-5.2、Kimi、Haiku | 分類、一覧化、単純変換、候補抽出を担当。コードの機械変換はKimi、Claude限定ツールが必要な場合のみHaikuを使う。 |

### 推奨teammate構成例

#### 標準開発チーム

| alias | remap先 | 役割 |
|---|---|---|
| `fable` | `gpt-5.6-sol` | 設計批判、難バグ、独立レビュー |
| `sonnet` | `kimi-for-coding` | 実装、テスト、修正反復 |
| `haiku` | `glm-4.5-air` | 探索、分類、バルク処理 |

親は実Fable-5とし、**親とteammateを異なるベンダーにする**のが重要である。

#### 長文解析チーム

| alias | remap先 | 役割 |
|---|---|---|
| `fable` | `gpt-5.6-sol` | 原因仮説と反証 |
| `sonnet` | `claude-sonnet-5` | Claude限定ツール利用 |
| `haiku` | `gpt-5.6-luna` | ログの分類・索引作成 |

メインをOpus-5[1m]にして、全文保持と証拠管理を担当させる。

#### CTF／securityチーム

| alias | remap先 | 役割 |
|---|---|---|
| `fable` | `gpt-5.6-sol` | 攻撃経路、暗号・プロトコル推論 |
| `sonnet` | `kimi-for-coding` | PoC、デコーダ、解析スクリプト |
| `haiku` | `glm-4.5-air` | IOC、文字列、ログの機械分類 |

メインFableがスコープ、証拠水準、安全性、最終回答を管理する。

## 2. モデルごとの実用的な強みと弱み

| モデル | 主な強み | 避けたい使い方 |
|---|---|---|
| **claude-fable-5** | 高難度の判断、レビュー、曖昧な状況での優先順位付け、オーケストレーション | grep相当の探索、定型コード生成、大量分類。同じFableで作成と最終レビューを完結させること |
| **claude-opus-5[1m]** | 巨大コンテキスト、複数資料の統合、難しい実装、長時間セッション | 短い単純タスクへの常用。巨大履歴を抱えたまま非Claudeモデルへ切り替える運用 |
| **claude-sonnet-5** | 品質・速度のバランス、調査、通常実装、Claudeツール利用 | 最難関の判断を単独で確定すること、極端なバルク処理 |
| **claude-haiku-4-5** | 低遅延、検索補助、要約、Claude限定ツールを使う軽作業 | 長い因果推論、最終セキュリティ判定、大規模設計 |
| **gpt-5.6-sol** | 深い推論、デバッグ、反証、CTF、独立レビュー | 単純な整形や分類。Claude専用ツールが必要な作業をそのまま任せること |
| **gpt-5.6-terra** | 通常難度の汎用実装・分析ワーカーとして使いやすい | Fable/Sol級の最終判断を無検証で代替すること。実タスクでSolとの差を継続計測すべき |
| **gpt-5.6-luna** | 高速な候補抽出、短い修正、背景処理 | 複数段階の難しい推論、最終レビュー |
| **gpt-5.5** | 成熟した予備系、5.6系障害時の互換的fallback | 5.6系が正常かつ余っている状況での優先使用 |
| **kimi-for-coding** | 明確な仕様からの実装、パッチ生成、テスト、コード反復 | 要件の採否判断、セキュリティ上の最終結論、曖昧なアーキテクチャ決定 |
| **glm-5.2** | 汎用ドラフト、バルク分析、別ベンダー視点 | 高リスク判断を単独で確定すること |
| **glm-4.5-air** | 大量の軽作業、分類、整形、背景探索 | 高精度が必要な推論や、誤りが後工程へ連鎖するタスク |

Terra、Luna、GLM系は公開ベンチマーク上の序列より、手元の実タスクで測った **成功率・修正回数・所要時間**を優先して配置を更新するのがよい。

## 3. 定額枠を燃やす優先方針

### 基本原則

「最も早く失効する枠」だけでなく、次の指標で優先度を決める。

\[
\text{消化緊急度}
=
\frac{\text{未使用率} \times \text{そのモデルへの適合度}}
{\text{リセットまでの時間}}
\]

さらに、重要タスクでは品質係数を掛ける。

\[
\text{実行優先度}
=
\text{消化緊急度}
\times
\text{期待成功率}
\]

### 現状での推奨順序

1. **Claudeの5時間枠**
   - 最も再生周期が短いため、Claude限定ツール、Fableの判断、Haiku/Sonnetの軽作業に積極利用する。
   - ただし、消化目的でFableに機械作業をさせない。適合するClaude作業を前倒しする。

2. **Codex Proの7日枠**
   - 使用率6%なら明確に余っているため、Solを難しいsubagent・独立レビュー・CTF担当として常用する。
   - 通常実装はTerra、背景作業はLunaへ流し、5.6系全体の実効消化率を上げる。

3. **Kimi coding plan**
   - 仕様確定後のコード生成を優先的に吸収させる。
   - 「Fableで設計 → Kimiで実装 → SolまたはFableでレビュー」が価値密度の高い流れになる。

4. **Z.ai plan**
   - GLM-4.5-airを大量低価値処理の第一候補、GLM-5.2を文書初稿や汎用セカンドオピニオンにする。
   - 軽作業を上位モデルから剥がすための基礎負荷として使う。

5. **Claude週次枠**
   - 現状は数%なので温存局面ではない。ただし5時間枠を無計画に使い切ると週次枠へ累積するため、定期的に両方の残量を見る。
   - 週次枠が逼迫したら、実装をKimi/Terra、深い推論をSol、バルクをGLM/Lunaへ移す。

### 実務上の判断

- **残量が十分な平常時**：品質最優先でFableを親に固定
- **Claude週次枠が50%以下**：Sonnet/Opusの通常実装をKimi/Terraへ移動
- **Claude週次枠が20%以下**：Claudeはツール必須作業と最終判断に限定
- **Codex残量が大幅に余る週後半**：Solによる独立レビュー、難バグ再検証、security仮説検証を増やす
- **Kimi/Z.aiの更新日が近い**：仕様確定済みバックログとバルク処理をまとめて投入

## 4. 代表的な起動コマンド

> 以下は提示された `--model`、`--fast`、`--subagent` インターフェースに基づく。teammateのalias remapは起動時設定として別途適用する。

### 高品質な標準オーケストレーション

```bash
claude-integ \
  --model=claude-fable-5 \
  --fast=glm-4.5-air \
  --subagent=gpt-5.6-sol
```

Fableが判断し、Solが難しい調査・反証、GLM Airが軽作業を担当する。通常の第一選択。

### 巨大ログ・長文コンテキスト

```bash
claude-integ \
  --model='claude-opus-5[1m]' \
  --fast=claude-haiku-4-5 \
  --subagent=gpt-5.6-sol
```

Opusが証拠集合を保持し、Solが原因仮説を独立検証する。`[1m]`はzshのglobを避けるため引用する。

### 実装スプリント

```bash
claude-integ \
  --model=gpt-5.6-sol \
  --fast=gpt-5.6-luna \
  --subagent=kimi-for-coding
```

Solが設計・デバッグを担当し、Kimiへ実装を委譲する。Claude専用WebSearch/ToolSearchが不要なセッション向け。

### CTF／認可済みsecurity作業

```bash
claude-integ \
  --model=claude-fable-5 \
  --fast=glm-4.5-air \
  --subagent=gpt-5.6-sol
```

メインがスコープと証拠水準を管理し、Solが攻撃仮説を担当する。起動時teammate remapでKimiをPoC担当として追加するとよい。

### 大量変換・低価値バルク

```bash
claude-integ \
  --model=glm-5.2 \
  --fast=glm-4.5-air \
  --subagent=kimi-for-coding
```

文書・データ処理はGLM、コード変換だけKimiへ流す。成果物は別セッションのFable/Solでサンプリングレビューする。

## 5. Fallbackチェーン

| 用途 | 推奨fallbackチェーン |
|---|---|
| トップ判断 | Fable-5 → gpt-5.6-sol → Opus-5[1m] → Sonnet-5 → gpt-5.5 |
| 難しい推論・デバッグ | gpt-5.6-sol → Fable-5 → Opus-5[1m] → gpt-5.5 → Sonnet-5 |
| 通常実装 | Kimi → Terra → Sonnet-5 → Sol → gpt-5.5 |
| 長文コンテキスト | Opus-5[1m] → 新規セッションのSolへ圧縮ハンドオフ → Fable → Sonnet |
| background／バルク | GLM-4.5-air → Luna → Haiku-4.5 → GLM-5.2 |
| Claude限定WebSearch/ToolSearch | Haiku-4.5 → Sonnet-5 → Opus-5[1m] → Fable-5 |
| CTF／security推論 | Sol → Fable-5 → Opus-5[1m] → gpt-5.5 |
| PoC・解析コード | Kimi → Terra → Sol → Sonnet-5 |
| 文書初稿 | GLM-5.2 → Sonnet-5 → Terra → Fable-5 |
| 最終セキュリティレビュー | Fable＋Solの二重判定 → Fable＋Opus → Sol＋Sonnet |

高重要度タスクでは、fallbackを単なる代替ではなく、**異なるベンダーによる再検証**として利用する。特に「最初のモデルが強く確信している」ことは、同一モデルで再質問するよりクロスベンダー確認を優先する理由になる。

## 6. 制約を踏まえた注意点

### WebSearch／ToolSearchはClaudeモデルに寄せる

- 検索が必要な調査は、最初からHaiku/Sonnet/Opus/Fableをメインまたは該当subagentに置く。
- SolやKimiをメインにしてから検索が必要になった場合は、Claude担当へ明示委譲する。
- 「検索だけHaiku → 読解と判断はSol/Fable」という二段構成が効率的。

### 重いClaude履歴から他ベンダーへ途中切替しない

Claude履歴が巨大化した後の `/model` 切替は400の原因になりうるため、次の順序を標準化する。

1. Claude側で結論、未解決点、証拠、重要ファイル位置を圧縮
2. 生ログや全履歴ではなく、構造化ハンドオフを作成
3. **新規セッション**で他ベンダーを起動
4. 必要な原資料だけ再添付

特にOpus-5[1m]の長時間セッションは、途中切替より新規セッションへのハンドオフを原則とする。

### `/model` 切替は軽い履歴のうちに行う

- 同一セッションでのベンダー混在は、探索初期や短い履歴では有効。
- どのモデルが主作業を行うかは、可能なら開始時点で決める。
- 長文化が予想される場合、最初からOpusまたは対象ベンダーをメインにする。

### teammate remapは起動前に設計する

teammateの混成は起動時remapで固定されるため、少なくとも次のプリセットを用意するとよい。

- `dev`：Sol＋Kimi＋GLM Air
- `research`：Sol＋Sonnet＋Luna
- `long-context`：Sol＋Sonnet＋Luna、メインOpus
- `security`：Sol＋Kimi＋GLM Air
- `claude-tools`：Sonnet＋Haiku＋Sol

セッション途中で必要ロールが変わりそうなら、汎用性の高いSol、Kimi、軽量モデルの3系統を置く。

### Opusのfastモードとランチャーの`--fast`を区別する

- Claude Codeの**fastモード**はOpusの出力を高速化する実行モードであり、小型モデルへのダウングレードではない。
- ランチャーの`--fast`はbackground/fastロールのモデル割り当て。
- 名称が似ているため、設定や運用ドキュメントでは「Opus fast mode」と「background fast role」を明確に分ける。

### 1Mコンテキストを無制限なログ置き場にしない

- 先にファイル索引、タイムライン、エラー分類をHaiku/Luna/GLM Airで作る。
- Opusには、原資料と索引を対応付けて渡す。
- 結論ごとに根拠位置を残し、後続のFable/Solが全文を再読しなくても検証可能にする。

### 親とレビュアーのモデルを分ける

Fableが計画、実装、レビューをすべて行うと、能力が高くても同じ前提誤りを引き継ぎやすい。推奨パターンは以下である。

```text
Fableで計画
  → Kimi/Terraで実装
  → Solで反証・テスト
  → Fableで証拠を基に採否決定
```

長文案件では次の形にする。

```text
Opusで証拠抽出
  → Solで原因仮説
  → Kimiで修正
  → Fableで最終レビュー
```

### モデル評価は「回答の印象」ではなく再作業量で測る

月次または週次で、ロールごとに次を記録する。

- 一発成功率
- テスト通過までの修正回数
- 人間またはFableによる差し戻し率
- 完了までの壁時計時間
- 誤った高確信回答の件数
- 消費枠とリセット時の未使用率

最終的には、モデル単体の一般評価よりも、**手元のタスクで最も少ない再作業で完了する配置**を正解とする。
